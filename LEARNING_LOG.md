### 2026-07-06 · docs · Delta-ratio evaluation method (false alarms per attack caught)
Recorded the builder's evaluation lens: for any model change, weigh attacks caught (ΔFN) vs false alarms added (ΔFP); the **delta ratio = ΔFP/ΔFN = false alarms per attack caught**, judged against the security cost of a miss. Exact (baseline → +class_weight): **Tree +44 caught / −15 alarms (strict win)**; **RBF-500k 1:1.25**; RBF-50k 1:1.83; LinearSVC 1:2.31. Data scaling (RBF baseline 50k→500k): +4,251 caught / +8 alarms = **1:0.002 (near-free recall)**. Insight: more data = near-free recall (better boundary); class_weight = traded recall, and the trade is cheaper on a better boundary (500k 1.25 < linear 2.31). Added a delta-ratio section to `07_comparison.ipynb`; `foundation.md` Section 12 primary-metric resolved to recall + delta ratio.

### 2026-07-06 · feature · SVM scaling experiment — RBF at 500k (data helps, but the wall is real)
Ran RBF SVC on a 500k stratified subsample (10x the 50k run) to test whether more data closes the gap to the tree. **Result: acc 0.9704, recall 0.9190, precision 0.9300; FN 9,030 / FP 7,712.** Cost: fit 1338s (~22 min) + predict 800s (~13 min) = ~35 min, 38,768 support vectors. LinearSVC at 500k: acc 0.9448 / recall 0.8832 (~= its full-2.26M 0.9412/0.8875, so data is NOT the linear bottleneck).
Insight: more data **did** help the RBF (recall 0.8809 -> 0.9190, ~4k fewer missed attacks) -- data starvation was a real factor, correcting my earlier lean. But still far from the tree (0.9190 vs 0.9984 recall; 9,030 vs ~178 missed), and the cost was brutal (10x data -> ~18x wall-clock for +0.04 recall). Kernel-SVM scaling = diminishing returns at exploding cost. Remaining gap is model fit (threshold splits vs smooth margin) + untreated imbalance. Next: class_weight on all three.

### 2026-07-06 · feature · Sprint 5 — LinearSVC baseline (underperforms the tree)
`notebooks/05_svm.ipynb`: featured split (67 feat) -> StandardScaler (fit on train only) -> LinearSVC (dual=False, no class_weight). Fit 231s, converged in 29 iters. **Result: test acc 0.9412, recall 0.8875, precision 0.8268; FN 12,550 / FP 20,733** -- well below the bucketed tree (0.9990 / 0.9984, ~178 missed). Train acc == test acc (0.9412), so no overfit.
Insight: the linear SVM **underfits** -- one straight hyperplane can't carve what the tree's many splits could, i.e. the classes aren't linearly separable. Scaling worked fine (converged, not the bottleneck); the gap is linearity -> next is **RBF on a subsample** (kernel = non-linear boundary). class_weight / RobustScaler are secondary (won't close a ~6-point linearity gap).

### 2026-07-06 · feature · Sprint 4 — leakage measured; it does NOT inflate the score
Built `notebooks/04_leakage.ipynb` (non-destructive; loads the persisted split). Full unpruned tree (depth 67, **3,109 leaves**): all test 0.9988 acc / 0.9966 recall; **leaked 0.9969 / 0.9959; clean (unseen) 0.9991 / 0.9969**.
**Correction:** my earlier hypothesis (small train–test gap ⇒ duplicate leakage inflating the 0.9988) is **refuted**. clean ≥ overall — leaked rows are if anything *harder*, so leakage inflated nothing; the honest number is ~0.999. Caveat: measures *exact* twins only (near-duplicates uncounted — matters more for SVM than trees). ### 2026-07-06 · study · Consolidation — `02_cleaning` reviewed (leakage boundary, stratification)
Discussion-only walk of `02`. Organizing idea: the **leakage boundary** — row-local ops (rename, binarize, clip-to-a-fixed-constant) are safe either side of the split; *fitted* ops (mean/max/scale — *learned* from data) must be train-only, post-split (`Section 7 #10`). Then the split's sharp point: it stratifies on the 15-class `label`, not the binary target — `label_binary` is the *question* (`y`), `label` is the *divider*.
