## Summary

This is Layer 0 of Caught: five service skeletons + docker-compose, three JSON-Schema contracts with Python/TypeScript codegen, and a ported featurizer with a frozen artifact and golden-fixture parity test. I did not just read this change, I ran it: brought up the full `docker compose` stack (all five containers healthy, `/health` returns 200, logs clean), ran the real codegen pipeline in both languages (`validate.py` and `tsc --noEmit` both pass), and — using the actual local CICIDS dataset and v1 parquet that happen to be present on this machine — regenerated `featurizer_meta.json` and `golden_fixture.json` from scratch and diffed them byte-for-byte against what's committed (identical), and reproduced the claimed drift-guard result (skipping the clip step fails exactly 7 of 25 fixture rows). The featurizer's transform logic is a faithful, careful port of `02`/`02b` — I traced every step against the notebooks line by line and it matches, including non-obvious details like the asymmetric clip list and the column order that falls out of `X.drop(columns=['destination_port']).join(oh)`.

The two headline problems are both about robustness of the *proof*, not the *logic*: the golden-fixture generator re-globs the raw CSVs in a fresh process and pairs them against a separately-generated, pre-existing parquet purely by index — exactly the failure mode the spec's own build plan explicitly warns against (and that an earlier architect-level review already flagged once). I demonstrated concretely that a plausible alternate file ordering breaks 20 of 25 pairings, and that the fixture's own sanity check misses 7 of those. Separately, the featurizer's input validation has two real gaps where malformed input sails past `_validate()` and then crashes with a raw, unhandled pandas/Python exception instead of the clean, documented rejection.

## Major

### 🟠 Golden fixture pairing depends on an unverified second glob, contradicting the spec's explicit instruction, `system/ml-service/featurizer/tests/generate_fixture.py:107-108`

**Problem**: The spec (`system/docs/specs/0001-layer-0-foundation/index.md`, Build plan step 5) is explicit: "generate the fixture in a single pipeline run ... never re derive raw row N with a second glob, whose file order is filesystem dependent and unsorted." `generate_fixture.py` does exactly what this forbids: it globs the raw CSVs fresh (`raw = pd.concat((pd.read_csv(f) for f in glob(RAW_GLOB)), ignore_index=True)`, line 107) in a brand-new process, then pairs rows with `featured = pd.read_parquet(FEATURED)` (line 108) — a *pre-existing*, separately-generated parquet — purely by positional/row index. The only protection is a sanity check that the raw row's `destination_port` IANA bucket agrees with the featured row's one-hot bucket (lines ~136-145).

I verified this is a real, not theoretical, risk:
- `glob()` on this machine is stable across repeated calls but is **not** sorted (confirmed: `glob(...) != sorted(glob(...))`), i.e. it depends on directory/filesystem order exactly as the spec warns.
- I regenerated the fixture fresh here and it happened to be byte-identical to committed (this machine's glob order matches whatever order originally produced `X_train.parquet`) — so today's fixture is *not* currently broken.
- I then simulated an entirely ordinary alternate ordering (`sorted(glob(...))` — the order a different OS, a fresh checkout, or a CI runner extracting the dataset zip could easily produce) and re-derived what each fixture row's "raw" half would be under that order. **20 of the 25 committed fixture rows would pair with a completely different real flow.**
- Of those 20, the destination-port sanity check catches only 13 (different IANA bucket). The other **7 slip through the sanity check** because the wrong flow happens to land in the same bucket (e.g. fixture index 1682916: committed raw port 80, alternate-order raw port 53 — both `well_known`).
- I then ran `featurize()` on those 7 "slipped-through" mispaired rows against the fixture's stored `expected` output: all 7 still failed on 31-56 of the 67 columns. So the practical failure mode is not a silent false-pass — the full parity test would still fail loudly under a different glob order — but it fails for a *confusing* reason: it looks exactly like a featurizer regression, not a fixture-generation artifact, and would send whoever hits it chasing the wrong bug.

Notably, `system/context/progress-log.md`'s 2026-08-12 entry for the spec design says an earlier Sonnet cross-check already caught "golden-fixture mispairing via an unsorted glob" and it was supposedly fixed at the spec level (the build-plan wording above is that fix). The implementation adopted the spec's *mitigation* (the sanity check) but not its *prevention* (single pipeline run, no second glob), so the underlying fragility is still live in the code, just narrower.

**Why it matters**: The golden fixture is the entire proof mechanism for AC-6, the project's stated deepest risk. Right now it happens to be correctly paired only because this machine's glob order happens to match whatever order was in effect when `X_train.parquet` was generated. The moment the fixture is regenerated on a different machine, a fresh checkout, or CI (the spec's own Consequences section anticipates regeneration), a large fraction of the fixture could silently repoint to different flows, and the resulting failure would misdirect debugging effort toward the featurizer rather than the fixture.

**Suggested fix**: Do what the spec actually asked for: in `generate_fixture.py`, snapshot the sample raw rows immediately after the (single) raw concat, then carry those same in-memory rows through the real `02`/`02b` transform steps in the same process to produce `expected`, instead of reading a separately-generated parquet by index. If reusing the pre-built parquet is preferred for speed, at minimum sort the glob deterministically in both this script and whatever regenerates `X_train.parquet`, and strengthen the sanity check to compare more than one untouched field (e.g. also cross-check `flow_duration` or packet counts, which are far less likely to coincidentally collide than a 3-bucket categorical).

### 🟠 A numeric-string `destination_port` passes validation but crashes later with an unhandled, unclear error, `system/ml-service/featurizer/featurizer.py:132-140` (validation) vs `:106` (crash site)

**Problem**: `_validate()`'s port check is:
```
port = row["destination_port"]
try:
    port_ok = float(port).is_integer() and 0 <= int(port) <= 65535
except (TypeError, ValueError):
    port_ok = False
```
This accepts a numeric *string* like `"80"` as valid (`float("80").is_integer()` and `int("80")` both succeed without raising). But `_validate()` never coerces the stored value — `row["destination_port"]` stays a `str`. Later, `pd.cut(frame["destination_port"], bins=_PORT_BINS, ...)` (line 106) needs to compare that value against the numeric bin edges and raises an **unhandled** `TypeError: '<' not supported between instances of 'int' and 'str'`.

I confirmed this empirically against the real module:
```
port = "80"   -> REJECTED, but with TypeError: '<' not supported between instances of 'int' and 'str'
```
compared to the documented/intended behavior for genuinely invalid input (port 70000, port -1, port 80.5, port None), which all correctly raise the clean, intended `ValueError: [featurizer] destination_port must be an integer in 0..65535, got ...`.

**Why it matters**: The spec and the featurizer's own docstring/README both promise "a missing field, an out of range port, or a negative duration ... is rejected with a clear error, not silently classified." A numeric-string port is a plausible shape for JSON-produced input (and the try/except-around-`float()/int()` pattern only makes sense as an attempt to tolerate exactly this shape), so this isn't a contrived edge case — it's the input class the code was visibly trying to handle and doesn't. When K1 wires this into `POST /predict`, this will surface as an unhandled 500 rather than a clean validation error, and if the endpoint's error handling specifically catches `ValueError` (the type every other check in `_validate` raises), this `TypeError` slips past it entirely.

**Suggested fix**: After the port check passes, normalize `row["destination_port"] = int(port)` so every downstream step sees a real `int`. Same applies anywhere else in `_validate` that tolerates a coercible type without persisting the coercion.

## Minor

### 🟡 An explicit JSON `null` for `flow_duration` skips validation and crashes during dtype casting instead of being rejected, `system/ml-service/featurizer/featurizer.py:128-130` and `:142-143`

**Problem**: The "missing" check (`missing = [c for c in self._required if c not in row]`) only checks *key presence*, not that the value is non-null. `duration = row.get("flow_duration"); if duration is not None and float(duration) < 0: ...` then explicitly skips the negative check when `duration is None`. So `{"flow_duration": null, ...}` passes `_validate()` entirely. I confirmed the actual failure: it crashes later, during `frame.astype(self.dtypes)`, with `TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'` — again an unhandled, low-level error rather than the intended clean rejection.

**Why it matters**: Same category as the Major above (validation promises a clean error, a malformed-but-plausible input instead gets an opaque crash), but a JSON-explicit `null` is a less likely real-world shape than a numeric string, so this is lower severity.

**Suggested fix**: Treat an explicitly-`null` required field the same as a missing one in the presence check, or validate non-null-ness for every field in `_required`, not just the two spot-checked ones.

### 🟡 No committed lockfile for `backend` or `frontend`; Dockerfiles use `npm install`, not `npm ci`, `system/backend/Dockerfile:10`, `system/frontend/Dockerfile:9`

**Problem**: Neither `system/backend/` nor `system/frontend/` has a `package-lock.json` in this change, and both Dockerfiles run `RUN npm install` against loose semver ranges (`^19.0.0`, `^11.0.0`, `^6.0.0`, ...). Every image rebuild re-resolves the dependency tree, so two builds days apart can silently pull different transitive versions.

**Why it matters**: `devops.md` Section 1 states dev is "`docker-compose up` ... One command, reproducible." A missing lockfile with unpinned installs undercuts that claim, and it's inconsistent with the rest of this same change: `system/ml-service/requirements.txt` explicitly comments that exact pins are deferred to K1 *with a stated reason*, and `system/shared/codegen/typescript/package-lock.json` **is** committed. The backend/frontend gap has no equivalent acknowledgment, so it reads as an oversight rather than a deliberate, documented deferral.

**Suggested fix**: Run `npm install` once locally to generate `package-lock.json` for both services, commit it, and switch the Dockerfiles to `npm ci`. If deliberately deferred like the Python pins, say so with a comment and a target slice.

### 🟡 `reindex(columns=self.feature_order)` can silently manufacture a NaN column instead of failing loudly on a future name mismatch, `system/ml-service/featurizer/featurizer.py:118-119`

**Problem**: The last two real steps are `frame = frame.reindex(columns=self.feature_order)` then `.astype(self.dtypes)`. `reindex` silently introduces an all-NaN column for any `feature_order` name not present in `frame` — it does not raise. Today this can't actually happen: `_required` is derived from `feature_order` itself (every non-`port_` entry, plus `destination_port`), so every needed raw field is validated present, and nothing after validation removes a required column. But it's not asserted anywhere, and for a `float64`-typed column, NaN is a perfectly legal value that casts cleanly — so if a future edit to `_DROP_COLS`, `_CLIP_COLS`, or the artifact's `feature_order` ever drifts out of lockstep with `_required`, this is the one path that could defeat the "fails loudly on any drift" invariant the spec calls out, for exactly the reason the spec worries about elsewhere (silent NaN from `pd.cut`/reindex-style operations).

**Why it matters**: Low likelihood today (verified: `_required`'s derivation currently covers `feature_order` exactly), but it's the single spot in an otherwise well-guarded pipeline with no explicit assertion, in a module whose entire purpose is "never silently wrong."

**Suggested fix**: Before the reindex, assert `set(frame.columns) == set(self.feature_order)` (or check for post-reindex NaNs) and raise a clear internal error if not.
